# Phase 7b: AUTORESEARCH — Validate Through Experimentation

**Metaphor:** Before the blacksmith declares the blade finished, they test it — cutting, bending, striking. Not just visual inspection. Real-world stress under real-world conditions.

**Duration:** 1-3 hours per epic (can run overnight for long experiments)
**Mode applicability:** GREENFIELD, FEATURE, REFACTOR, SECURE
**Inspired by:** Andrej Karpathy's AutoResearch pattern — humans direct research strategy, agents handle execution

---

## What Happens

After TEMPER ships working code and before RALPH LOOP captures learnings, AutoResearch runs experiments against the live codebase to validate that improvements actually work at runtime. This is NOT more testing — it's experimentation. Tests verify expected behavior. Experiments discover unexpected behavior.

### The Core Pattern (from Karpathy)

```
program.md (research protocol)  ← Human writes the questions
       ↓
   Agent Loop                   ← Agents run experiments autonomously
       ↓
   Results + Signal             ← Each cycle MUST produce new signal or terminate
       ↓
   Ratchet Decision             ← Keep what works, revert what doesn't
       ↓
   Repeat or Terminate          ← Max iterations configurable (default: 5)
```

Three non-negotiable principles:
1. **Humans direct, agents execute** — the `program.md` defines WHAT to investigate, agents figure out HOW
2. **Ratchet only advances** — findings accumulate, never regress. Each cycle adds knowledge.
3. **Termination is mandatory** — no infinite loops. If no new signal after 2 cycles → stop.

### Inputs
- Merged code from TEMPER (on main, deployed to staging)
- The epic's FSDs and acceptance criteria
- Anti-regression baseline
- Red-Team Report findings (from TEMPER Step 5c)

### Process

#### Step 1: Write the Research Protocol (`program.md`)

Before agents run, the human (or lead AI) writes a `program.md` that defines what to investigate. This is the Karpathy innovation — the protocol is human-authored research strategy, not agent-generated busywork.

```markdown
# AutoResearch Protocol — [Epic Name]

## Questions to Answer
1. Does the new ticket routing handle 500+ concurrent assignments without degradation?
2. Does the optimistic UI update correctly reconcile when the server rejects?
3. What happens to existing data when the migration adds the NOT NULL column?

## Experiment Types
- [ ] Load test: 500 concurrent users on ticket assignment endpoint
- [ ] Chaos test: Kill server mid-optimistic-update, verify client recovery
- [ ] Data migration: Run migration against production-clone with real data

## Success Criteria
- P95 latency < 200ms under load
- Zero orphaned optimistic states after server rejection
- Zero data loss during migration

## Max Iterations: 5
## Terminate If: No new signal after 2 consecutive cycles
```

**Rules for `program.md`:**
- Written BEFORE agents start (not generated by agents)
- Questions must be specific and measurable (not "does it work well?")
- Success criteria must be quantitative where possible
- Max iterations MUST be set (default: 5, max: 10)
- Termination condition MUST be set

#### Step 2: Agent Experiment Loop

Each cycle follows this pattern:

```
CYCLE N:
  1. READ program.md + previous cycle results
  2. PICK the highest-priority unanswered question
  3. DESIGN a minimal experiment to answer it
  4. EXECUTE the experiment (real code, real runtime, real data)
  5. RECORD results in findings.md (append-only)
  6. DECIDE: new signal found?
     - YES → update program.md with refined questions, continue
     - NO → terminate (ratchet rule: 2 cycles without signal = stop)
```

**Experiment types available:**

| Type | What It Does | When to Use |
|------|-------------|-------------|
| **Load Test** | Simulated concurrent users/requests | New endpoints, changed queries |
| **Chaos Test** | Kill services, drop connections, corrupt inputs | State sync, recovery paths |
| **Data Experiment** | Run against production-clone data | Migrations, schema changes |
| **A/B Comparison** | Before vs after performance metrics | Refactors, optimizations |
| **Edge Case Discovery** | Fuzz inputs, boundary values, race conditions | Any new feature |
| **Regression Hunt** | Automated exploration of unchanged features | Refactors (CRITICAL) |

#### Step 3: The Ratchet

After each cycle, the ratchet rule applies:

```
findings.md (append-only):

## Cycle 1 — 2026-03-30 14:00
Question: P95 latency under 500 concurrent users?
Experiment: k6 load test, 500 VUs, 5 minutes
Result: P95 = 340ms (EXCEEDS 200ms target)
Signal: YES — identified N+1 query in ticket assignment
Action: Fix N+1, re-run in next cycle

## Cycle 2 — 2026-03-30 14:30
Question: P95 latency after N+1 fix?
Experiment: Same k6 script, same parameters
Result: P95 = 87ms (PASSES 200ms target)
Signal: YES — confirmed fix works
Action: Keep fix, move to next question

## Cycle 3 — 2026-03-30 15:00
Question: Optimistic UI reconciliation after server rejection?
Experiment: Intercept API response with 409 Conflict, verify UI rollback
Result: UI correctly rolls back, but spinner persists for 3 seconds
Signal: YES — found UX issue in error recovery path
Action: Fix spinner cleanup, add to findings
```

**Ratchet rules:**
- `findings.md` is append-only — never delete previous cycle results
- Each cycle must produce a YES/NO signal assessment
- 2 consecutive NO signals → AutoResearch terminates
- Findings that require code changes → create GitHub issues, don't fix inline (AutoResearch is observation, not implementation)
- Exception: trivial fixes (< 5 lines, no architectural impact) can be fixed inline and verified in the next cycle

#### Step 4: Synthesis

After the loop terminates, produce an **AutoResearch Report**:

```markdown
# AutoResearch Report — [Epic Name]

## Summary
- Cycles run: N of M max
- Questions answered: X of Y
- Issues discovered: Z (A critical, B non-critical)
- Termination reason: [all questions answered / no new signal / max iterations]

## Key Findings
1. [Finding] — [Impact] — [Action taken or issue created]
2. ...

## Regressions Detected
- [None / list with severity]

## Confidence Delta
- Pre-AutoResearch confidence: [from R7]
- Post-AutoResearch confidence: [updated score]
- Delta explanation: [what changed and why]

## Artifacts
- program.md: .foundry/autoresearch/program.md
- findings.md: .foundry/autoresearch/findings.md
- Load test results: .foundry/autoresearch/load-test/
- Screenshots: .foundry/autoresearch/screenshots/
```

### Outputs
- AutoResearch Report (`.foundry/autoresearch/report.md`)
- `program.md` (research protocol, `.foundry/autoresearch/program.md`)
- `findings.md` (cycle-by-cycle results, `.foundry/autoresearch/findings.md`)
- GitHub issues for any discovered problems
- Confidence delta (pre vs post)
- Updated anti-regression baseline (if experiments revealed new metrics to track)

## Why This Phase Exists

Testing answers: "Does the code do what we specified?"
AutoResearch answers: "Does the code do what we DIDN'T specify?"

Tests are written against known acceptance criteria. AutoResearch explores the unknown — what happens under load, what happens when things fail, what happens with real data at scale. This is the gap between "tests pass" and "production works."

**The Karpathy insight:** Humans are bad at running experiments (we run 2-3 and call it done). Agents can run 20-50 experiments in the same time. But agents are bad at deciding WHAT to experiment on (they optimize for coverage, not insight). The `program.md` pattern combines human research direction with agent execution capacity.

**IT Concierge evidence:** The migration verification gate (TEMPER Step 3b) caught ghost migrations. But AutoResearch would have also caught the N+1 queries in the ticket list view (4 seconds to load 50 tickets), the session leak under concurrent logins, and the Supabase RLS bypass when PgBouncer was in transaction mode — all of which were only discovered in production.

## ⚖️ R-AR: AutoResearch Gate

**Key question:** "Did experiments reveal anything that changes our confidence?"

**Must pass:**
- [ ] `program.md` written with specific, measurable questions
- [ ] At least 3 experiment cycles completed (or terminated early with documented reason)
- [ ] `findings.md` is append-only with signal assessment per cycle
- [ ] All critical findings have GitHub issues created
- [ ] No unresolved regressions
- [ ] Confidence delta documented (and explained if it went DOWN)
- [ ] AutoResearch Report produced (`.foundry/autoresearch/report.md`)
- [ ] If confidence dropped below 8 → findings feed back to HAMMER for fixes before RALPH LOOP
